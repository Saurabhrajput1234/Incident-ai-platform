Pending Agent Architecture & Implementation Report

Comprehensive Technical Guide: Components, Modifications, State Machines, LLM Pipeline & Flaw Resolutions
Incident AI Platform • Date: September 8, 2026 • Status: Production Verified
Executive Summary
The Pending Agent is an autonomous ITSM lifecycle agent designed to handle ServiceNow tickets entering On Hold / Pending states. It continuously monitors engineer work notes, analyzes what information or action is required from the caller using Groq LLM, manages an automatic 3-tier reminder cycle, generates simulated notification emails, preserves historical audit trails in PostgreSQL, and enforces clean state consistency across UI and backend services.

3. End-to-End Workflow & State Machine

The diagram below outlines the full lifecycle of an incident moving through the Pending Agent system:

Step 1: State Change Trigger
Incident state updates to On Hold (via manual engineer edit in UI or automatic Acknowledgement Agent classification).
↓
Step 2: Idempotency Gate (Cycle Preservation)
PendingService checks for an existing ACTIVE cycle in PostgreSQL.
• If an active cycle exists and reminder is not forced: Preserves cycle, retains timer, returns CYCLE_PRESERVED.
• If no active cycle exists: Advances to note analysis.
↓
Step 3: Multi-Note Context & Substantive Fallback
Fetches top 2 work notes (Note 0 + Note 1). If both are state transition messages (State changed to: ...), the query looks back for the most recent substantive note (e.g. manual engineer inquiry or system note) plus incident title and description.
↓
Step 4: Groq LLM Dynamic Extraction
Work notes and context are sent to Groq API (POST https://api.groq.com/openai/v1/chat/completions). LLM parses requirements and returns: {"is_caller_action_required": true, "reasoning": "...", "confidence": 0.98}.
↓
Step 5: Database Cycle Creation / Advancement
A new PendingCycle record is inserted (status: ACTIVE, reminder_count: 1/3, next_reminder_at: +24h). All transactions are explicitly committed and refreshed.
↓
Step 6: Work Note Audit Trail Generation
The full plain-text reminder email is rendered with exact details needed from caller. A structured work note (source_type: PENDING_AGENT, action_type: SEND_REMINDER) is appended containing the full email text and cycle ID.

4. Flaws Discovered, Erased & Solved

During development and live verification, several intricate architectural and concurrency issues were identified and permanently resolved:

Flaw 1: Unwanted Auto-Triage on Incident Updates (Reverting Active to On Hold)

  • Symptom: When an engineer clicked Edit and activated a ticket to In Progress, the UI refreshed and showed the ticket reverted to On Hold.
  • Root Cause: backend/app/api/v1/incidents.py had an automatic hook in update_incident: 
    if updated.state in ('new', 'in_progress'):
    background_tasks.add_task(_auto_triage_force, incident_id)
    This background task executed TriageAgent, which in turn called AcknowledgementAgent. The Acknowledgement Agent re-classified the description as a Salesforce request, changed state back to On Hold, and initiated a new pending cycle!
  • Solution: Completely removed _auto_triage_force and the background task from PUT /v1/incidents/{incident_id}. Triage now only triggers on initial creation or when explicitly run by the user. Manual edits permanently persist.

Flaw 2: Missing self.db Attribute on IncidentService

  • Symptom: Moving an incident from On Hold to In Progress logged an unhandled exception: 'IncidentService' object has no attribute 'db', and the pending cycle remained ACTIVE.
  • Root Cause: In IncidentService.__init__, the constructor initialized self.repo = IncidentRepository(db) but failed to store self.db = db. When update_incident called PendingCycleRepository(self.db) to cancel active cycles, Python raised an AttributeError.
  • Solution: Added self.db = db to IncidentService.__init__. Cycle cancellation now executes cleanly.

Flaw 3: SQLAlchemy Session Flush vs. Commit in PendingCycleRepository

  • Symptom: Cycle creations and state updates were lost upon HTTP request completion; database tables showed stale statuses.
  • Root Cause: PendingCycleRepository was executing await self.db.flush() instead of await self.db.commit(). FastAPI's database session dependency closes sessions upon response delivery, triggering an implicit rollback of uncommitted flushes.
  • Solution: Replaced all instances of flush() with await self.db.commit() and await self.db.refresh(cycle) across all repository methods.

Flaw 4: Consecutive State Change Notes Causing Silent Reminder Discard

  • Symptom: Manually setting a ticket to On Hold did not trigger the Pending Agent; no reminder note was generated and the pending cycle was missing.
  • Root Cause: In the work notes history, the two newest entries were:
    1. State changed to: on_hold...
    2. State changed to: in_progress...
    Because neither note asked a question, Groq LLM returned is_caller_action_required: false. A guard in service.py then took a DISCARDED branch and returned early without generating a reminder!
  • Solution:
    1. Updated PendingWorkNoteAnalyzer prompt to always enforce is_caller_action_required: true for tickets placed in On Hold.
    2. Enhanced note selection: if the top two notes are state changes, the algorithm looks back for the most recent substantive note (e.g. engineer question or acknowledgement text).
    3. Removed the discard branch in PendingService so reminder generation always executes on On Hold transitions.

Flaw 5: Work Note Attribution Mismatch

  • Symptom: State change notes added during manual edits were attributed to source_type: USER and name "User".
  • Root Cause: IncidentService.update_incident was defaulting source to USER.
  • Solution: Updated update_incident to attribute notes to WorkNoteSourceType.ENGINEER and the assigned engineer's name (or "Engineer" if unassigned).
